# Phone Clinic — Phase 1 analysis and design

**Scope:** Read-only analysis and future design. No application behavior or data was changed for this report. Observations below describe the checked-in source, not a live Firebase deployment.

## 1. Existing state

### 1.1 Spare parts and repairs

- `Product` has `buyPrice`, `sellPrice`, `stock`, optional `reference` and `barcode`, and optional `ownerId`; it has no explicit spare-part discriminator ([src/types.ts:8-21](../src/types.ts:8)). `RepairPart` stores `productId`, name, quantity, optional `unitBuyPrice`, `unitPrice`, and line `total`; `Repair.parts` is an array of those lines ([src/types.ts:134-141](../src/types.ts:134), [src/types.ts:150-173](../src/types.ts:150)).
- `isSparePart()` lowercases the concatenated name, category, reference, and barcode, then matches a fixed regular expression containing terms such as `piece`, `spare`, `repair`, `battery`, `screen`, and `module`; it returns false when the input or combined text is empty ([src/lib/utils.ts:8-20](../src/lib/utils.ts:8)). This is a text heuristic, not a persisted type/category invariant; a normal product can match accidentally, and a part whose fields lack one of those tokens will not match.
- `Products.tsx` subscribes to the store's `products` and `categories` ([src/components/Products.tsx:165-183](../src/components/Products.tsx:165)). Product create/edit saves `formData` (including price and stock) into `products`; initial stock creates a separate `supplies` record ([src/components/Products.tsx:316-360](../src/components/Products.tsx:316)). Restocking updates product stock and `buyPrice`, then writes a `supplies` record in a separate operation ([src/components/Products.tsx:397-428](../src/components/Products.tsx:397)). Product edit permits manual stock changes; the UI input has `min="0"` but that is not a data/rules invariant ([src/components/Products.tsx:1057-1061](../src/components/Products.tsx:1057)). The stock-history dialog derives entries from `supplies` and exits from `sales`; it does not read repair movements ([src/components/Products.tsx:448-505](../src/components/Products.tsx:448)).
- `Repairs.tsx` subscribes to repairs, clients, and the store's full product documents ([src/components/Repairs.tsx:107-133](../src/components/Repairs.tsx:107)). The selector filters those products with `isSparePart()`. Selecting a part copies `buyPrice` to `unitBuyPrice` and `sellPrice` to `unitPrice`; the resulting line `total` is based on the sell price ([src/components/Repairs.tsx:626-656](../src/components/Repairs.tsx:626)). The saved repair payload stores the `parts` array ([src/components/Repairs.tsx:770-790](../src/components/Repairs.tsx:770)).
- **Repair stock transactions currently present:**
  1. Creating a repair reads each referenced product in a Firestore transaction, subtracts the line quantity when the product exists, and writes the repair in the same transaction. It does not reject a missing product or check that stock is sufficient/nonnegative before subtraction ([src/components/Repairs.tsx:820-835](../src/components/Repairs.tsx:820)).
  2. Editing a repair computes old quantities as returns and new quantities as deductions, reads the affected products, applies the net deltas, and updates the repair in one transaction. It does not read the persisted repair in that transaction or validate the resulting stock ([src/components/Repairs.tsx:795-818](../src/components/Repairs.tsx:795)).
  3. Deleting a repair adds its saved part quantities back to products that still exist, then deletes the repair, in one transaction ([src/components/Repairs.tsx:52-66](../src/components/Repairs.tsx:52)).
  4. The repair status does not gate these stock changes: the create/edit paths above execute for the repair form's chosen status. A status-only transition has no separate stock movement path in the inspected code. Deletion restores the saved quantity regardless of status.
- The repair list calculates daily “net profit” for `livre` repairs as repair total minus the sum of saved `unitBuyPrice * quantity`, falling back to the product's current `buyPrice` when the saved cost is absent/nonpositive ([src/components/Repairs.tsx:235-251](../src/components/Repairs.tsx:235)). The fallback cannot establish the historical purchase cost. The form's “Coût des pièces” display is the sum of `RepairPart.total` (charged part prices), not purchase cost ([src/components/Repairs.tsx:633-634](../src/components/Repairs.tsx:633), [src/components/Repairs.tsx:972-997](../src/components/Repairs.tsx:972)).

### 1.3 Stock history, negative stock, and write consistency

- There is no general stock-movement ledger. `supplies` record inbound purchasing and product history infers sales exits from `sales`; repairs, manual edits, returns, and other adjustments are not represented in that history ([src/components/Products.tsx:448-505](../src/components/Products.tsx:448)). The UI itself calls out manual edits and offline synchronization as potential differences ([src/components/Products.tsx:1562-1576](../src/components/Products.tsx:1562)).
- POS does check available stock within its sale transaction before decrementing ([src/components/POS.tsx:569-615](../src/components/POS.tsx:569)). Repair creation subtracts without a transactional sufficiency check, so it can drive stock below zero; repair edits apply a stale-form diff without checking the persisted repair/resulting stock ([src/components/Repairs.tsx:795-835](../src/components/Repairs.tsx:795)). Product form's `min=0` is browser-side only and is not enforced by existing Firestore rules ([src/components/Products.tsx:1057-1061](../src/components/Products.tsx:1057); [firestore.rules:130-135](../firestore.rules:130)).
- Repair create uses a newly allocated document ID; two separately submitted create requests can therefore be separate tickets/deductions. Edits apply the same old/new diff to products without reading the current repair document/version, so duplicate or stale saves can apply that diff more than once. The current transaction retry behavior alone is not a business idempotency key.

The rules do not currently define `parts`, `part_costs`, employees, payroll, expenses, or stock movements; unmatched access is denied.

## 2. Field-level cost exposure and proposed protection

### Where a user who must not see costs can currently receive them

Firestore grants document access, not a projection of allowed fields. Today the following values can be delivered to a browser:

1. **`products/{id}.buyPrice`:** present in the `Product` type ([src/types.ts:8-18](../src/types.ts:8)). `products` read is allowed to any authenticated account with no menu/store test ([firestore.rules:130-135](../firestore.rules:130)). A Technicien repair listener downloads full product documents and the repair selector directly copies `buyPrice` into React state ([src/components/Repairs.tsx:127-133](../src/components/Repairs.tsx:127), [src/components/Repairs.tsx:640-656](../src/components/Repairs.tsx:640)). A Caissier/Vendeuse POS listener likewise receives whole product documents ([src/components/POS.tsx:67-74](../src/components/POS.tsx:67)).
2. **`repairs/{id}.parts[].unitBuyPrice`:** stored in the repair parts type and payload, including the purchase price copied when a technician selects a part ([src/types.ts:134-141](../src/types.ts:134), [src/components/Repairs.tsx:656](../src/components/Repairs.tsx:656), [src/components/Repairs.tsx:770-790](../src/components/Repairs.tsx:770)). Repair reads are intentionally granted to users with `reparation`, so technicians receive this field in the repair document ([firestore.rules:202-204](../firestore.rules:202)). The UI also computes/displays repair profit from it ([src/components/Repairs.tsx:235-251](../src/components/Repairs.tsx:235)).
3. **Sale snapshots:** POS adds `buyPrice` to the in-memory cart item ([src/components/POS.tsx:315-320](../src/components/POS.tsx:315)) and writes `items: cart` to the sale transaction ([src/components/POS.tsx:650-675](../src/components/POS.tsx:650)). `SaleItem`'s TypeScript interface does not declare `buyPrice` ([src/types.ts:33-41](../src/types.ts:33)), but that does not remove the runtime object property. `sales` read is allowed to every authenticated account ([firestore.rules:144-149](../firestore.rules:144)).
4. **`supplies` purchase data:** initial stock/replenishment records include `buyPrice` and `totalCost` ([src/components/Products.tsx:339-350](../src/components/Products.tsx:339), [src/components/Products.tsx:409-416](../src/components/Products.tsx:409)); the collection is readable by every authenticated account ([firestore.rules:194-200](../firestore.rules:194)).

The direct code references to `buyPrice`/`unitBuyPrice` are in `Products.tsx`, `POS.tsx`, `Dashboard.tsx`, `Repairs.tsx`, `SalesVolumeChart.tsx`, and `Settings.tsx` ([src/components/Products.tsx:236-238](../src/components/Products.tsx:236), [src/components/POS.tsx:318-485](../src/components/POS.tsx:318), [src/components/Dashboard.tsx:300-357](../src/components/Dashboard.tsx:300), [src/components/Repairs.tsx:241-243](../src/components/Repairs.tsx:241), [src/components/SalesVolumeChart.tsx:99-100](../src/components/SalesVolumeChart.tsx:99), [src/components/Settings.tsx:461-472](../src/components/Settings.tsx:461)). `Products`, `POS`, `Repairs`, `Dashboard`, `Invoices`, `Sales`, and `Settings` also fetch whole product documents; even if a component does not reference the field in an expression, Firestore has already delivered it ([src/components/Invoices.tsx:106](../src/components/Invoices.tsx:106), [src/components/Sales.tsx:264](../src/components/Sales.tsx:264)). Menus hide screens but do not protect these existing reads in rules.

### Recommended target

- Keep product identity, selling information, and stock in the canonical product document; move purchase costs for **all** products (not only spare parts) to an owner-only `product_costs/{productId}` document, containing at minimum `{ ownerId, productId, currentBuyPriceMilli, updatedAt, updatedBy }`. This avoids leaving regular POS item costs exposed merely because they are not repair parts.
- Keep public operational repair/sale snapshots cost-free: repair `parts[]` retains product ID/name, quantity, sell price, and charged line total, but not `unitBuyPrice`; sale `items[]` contains no `buyPrice`; `supplies` carries quantities/source/product but not purchase price/total cost. Historical cost and recognized amounts go to a separate owner-only financial journal (described in section 6), with immutable transaction-time cost snapshots.
- Put rules on `product_costs` and the financial journal requiring authenticated user profile `role == 'admin'`, `request.auth.uid == ownerId`, and the store's own `ownerId`; do not grant access merely because a profile has `pos`, `reparation`, or a platform-super-admin email. Menu checks still gate navigation, but cost confidentiality is the collection rule.
- Never fetch `product_costs` from technician/cashier screens. The repair workflow can show stock and selling price without any cost field. If it needs to calculate/display a margin, that screen must be owner-only; a technician endpoint must not return the margin or underlying cost.

### Non-destructive, reversible migration outline

1. Take a verified, access-controlled export/backup and inventory all existing cost-bearing documents. Record counts and owner partitions; identify duplicate/missing references and repairs with absent cost snapshots.
2. Add restrictive rules for the new private collection(s) first. Use a trusted Admin SDK migration (the existing server has Admin SDK access, but no migration route exists today) to copy product costs and historical sale/repair/supply cost facts. Do not treat a current `products.buyPrice` as a proven historical purchase price for old sales/repairs; mark reconstructed/missing history as estimated or unknown and preserve the original raw values in the protected backup.
3. Backfill `product_costs` from `products.buyPrice`; backfill repair snapshot facts from `parts[].unitBuyPrice` where present; where absent, preserve “unknown” rather than silently substituting current cost. For sale history, preserve any stored `items[].buyPrice`; otherwise use verified historic receipt/cost evidence or mark unknown. Copy supply `buyPrice`/`totalCost` as purchase evidence.
4. Verify per-owner document counts, values, totals, access with technician/cashier identities, and representative historical reports. Run in shadow/read-compare mode before switching readers.
5. Switch owner-only cost readers and cost writes to the private documents/journal. Remove cost reads from employee clients. Only after verification, scrub the old `buyPrice`, `unitBuyPrice`, and sale-item cost fields from all employee-readable documents and remove purchase amount fields from supplies. Keep the protected export until the rollback window closes.
6. Rollback means switch readers back to the retained private cost source or restore data under owner-only rules; **do not** restore plaintext fields while broad read rules are active. Maintain a migration marker/version and reconcile every partially completed batch before retrying.

This sequence preserves data and provides a controlled rollback, but confidentiality is not fully fixed until legacy fields are scrubbed (or rules are tightened to deny those documents to employee users, which would break POS/repair reads). Plan a short, explicit cutover window rather than describing the copy phase alone as a security fix.

## 3. Spare-parts collection decision

| Option | Benefits | Costs / risks |
|---|---|---|
| **A — Keep spare parts in `products` (recommended)** | Existing POS sells product documents and decrements their stock; Repairs already searches `products` and decrements the same stock ([src/components/POS.tsx:569-615](../src/components/POS.tsx:569), [src/components/Repairs.tsx:820-835](../src/components/Repairs.tsx:820)). One canonical quantity avoids double stock and requires the least migration. POS and repair behavior can remain on the same product IDs. | The current `isSparePart()` heuristic is ambiguous. A new explicit persisted discriminator (for example `kind: 'sparePart'`) needs a cautious backfill and validation. `products` must lose sensitive cost fields; non-part products need the same cost-protection solution. |
| **B — Create `parts` as a new collection** | Clear domain model and dedicated part-specific attributes, rules, and UI. Easier to make a parts-only catalog screen. | Existing POS and Repairs would need coordinated changes. A copied part also left in `products` creates two stock counts; a one-time copy does not keep POS sales and repair use synchronized. Migrating document IDs, historical repair/sale references, categories, barcodes, and stock creates more risk. It is safe only if one collection is the canonical stock owner and the other is a non-stock view/reference, or if all writers are migrated atomically. |

**Recommendation:** choose A for the near-term inventory phase: keep one canonical `products` document/stock for each sellable spare part; add an explicit `kind`/`isSparePart` marker and backfill it from the current heuristic for review. `isSparePart()` is currently a text match, not an authoritative catalog classification ([src/lib/utils.ts:8-20](../src/lib/utils.ts:8)). Do not duplicate stock in a new `parts` collection. Revisit B only as a deliberate catalog/POS migration with an explicit single-stock authority.

### Reference/barcode uniqueness

Firestore rules cannot perform a collection-wide uniqueness query. Use deterministic per-store lookup documents such as `product_identifiers/{ownerId}_{type}_{normalizedValueHash}`. Normalize references (trim and case-fold; decide punctuation policy) and barcodes (use one documented digit/code normalization) before key generation. In one transaction, read each new key, reject an existing key owned by another product, create/update the product, reserve new keys, and delete old keys only when they still point to that product. Apply the same atomic process when a product changes or is deleted. Use a safe key encoding/hash so arbitrary reference characters cannot form path segments; store the normalized value and product ID in the lookup to detect hash collisions. First audit and resolve current duplicates—rules alone cannot retrofit uniqueness.

## 4. Safe stock design

### Stock source, quantities, and movement document

Maintain a single integer on-hand quantity on the canonical product. Use an append-only `stock_movements/{movementId}` collection, partitioned by `ownerId`, with fields such as:

```text
ownerId, productId, quantityDelta, movementType,
sourceType, sourceId, sourceVersion, idempotencyKey,
occurredAt, actorUid, reason
```

Movement types should distinguish at least `receipt`, `sale`, `repair_use`, `repair_release`, `customer_return`, `supplier_return`, and `manual_adjustment`. Record cost only in the owner-only financial ledger, not in a movement visible to technicians. Corrections are compensating movements, never edits/deletes of prior movements. Require a reason and actor for manual adjustments.

### Repair save/edit algorithm

Adapt the current diff workflow without changing the repair form or status workflow:

1. Keep the submitted parts array as the desired final list. In a transaction, first read the persisted repair (for edits), current stock documents for all affected products, and any deterministic movement IDs needed; perform all reads before writes.
2. Compute the per-product net delta from the transaction-read persisted parts versus the desired final parts. For creates, the old list is empty. Validate every product exists, quantities are positive integers, the store matches, and `currentStock + delta >= 0`; reject the entire save if any check fails.
3. If a repeated request asks for the already-persisted parts list, the delta is zero: do not decrement again or write another movement. For a real change, increment the repair's `stockVersion` in that transaction and write deterministic movement IDs such as `${repairId}_${stockVersion}_${productId}` for the net movement, alongside stock and repair changes. The transaction-read persisted version prevents competing updates from silently replaying the same old diff; include an expected version in the request and reject stale edits or rebase them deliberately.
4. Keep status-only edits stock-neutral. Deleting a repair or transitioning it to a stock-releasing state must create compensating positive movements exactly once in the same transaction. Reopening must not deduct parts again if they remain assigned; a later parts change produces only a new net delta.
5. Ensure the POS sale path, restock/receipt, repair path, return path, and manual adjustment all use the same stock transaction/movement mechanism. POS currently checks stock and decrements in a transaction but writes no movement ([src/components/POS.tsx:569-615](../src/components/POS.tsx:569)).

For returns, require an original sale/repair reference and a deterministic return ID. Make “restock” versus “scrap/non-restock” an explicit return disposition; only restock increases available quantity. A repeated return request must hit the same idempotency key and must not add stock twice.

### Firestore rules: enforceable and non-enforceable boundaries

- Rules can reject a resulting product write when `stock < 0`, enforce owner/menu/actor constraints, validate permitted field changes, and—if the transaction schema is designed carefully—use `getAfter()` to require the paired movement and stock state to agree within one atomic write.
- Rules do not automatically make client code transactional, supply a stable idempotency key, or compute correct old-vs-new repair deltas. Rules do not provide collection-wide reference uniqueness. A UI `min` or client-side stock check is not security enforcement.
- A trusted server command (or a carefully tested rules-validated transaction design) should be the only authorized path for movements. For a high-integrity accounting and payroll ledger, prefer server-side transactional command handlers: Admin SDK bypasses rules, so each endpoint must authenticate the caller, verify store ownership/menu permissions itself, validate all input, and write the complete atomic transaction. Do not let browser code directly update stock if server-only authority is selected.

## 5. Permission matrix

Keep stored roles limited to `admin | user`; “Technicien” is already a user-profile preset, not a stored role. The UI offers a `technician` preset but persists `role: 'user'` and the selected menus ([src/components/Users.tsx:45-49](../src/components/Users.tsx:45), [src/components/Users.tsx:281-284](../src/components/Users.tsx:281)). `hasMenuAccess()` gates routes/navigation in the app ([src/App.tsx:172-195](../src/App.tsx:172), [src/App.tsx:849-858](../src/App.tsx:849)); that alone is not database security.

“Owner-only” in this proposal means profile `role == 'admin'` and `ownerId == that user's uid`. Do not interpret “admin” as every profile with some admin-like UI choice, nor inherit the current platform-admin bypass for cost data.

| Screen/data | Admin principal (owner) | Technicien (`role: user`, `['reparation']`) | Caissier/Vendeuse (`role: user`, `['pos']`) | Rules versus UI |
|---|---|---|---|---|
| Parts catalog: name, reference, barcode, selling price, on-hand availability | `pieces` (and required operational access) | `reparation` for selection/availability only; no independent cost-bearing inventory screen by default | `pos` for sale catalog/availability | UI hides menus; rules must enforce same-store reads, menu permission, and allowed write fields. Stock movement writes must be validated separately. |
| Purchase cost | Owner only; `pieces`/owner inventory screen | None | None | Enforce with owner-only `product_costs` rules. UI concealment is not protection. |
| Gross margin / profit | Owner only; `comptabilite` (and optionally owner dashboard) | None | None | Read only owner financial journal/derived data. Never include cost/margin in repair/sale documents returned to employee clients. |
| Accounting, expenses, cash reconciliation | Owner only; `comptabilite` | None | No accounting history; POS may collect a payment | Enforce on accounting ledger queries/writes in rules or owner-authenticated server endpoints; hiding nav is only UX. |
| Payroll, employee loans/advances | Owner only; `personnel` | None | None | Owner-only rules/server writes; never infer access from a `user` role preset. |
| Repair creation/edit, device details, part usage and sell price | `reparation` (admin access as configured) | `reparation`; stock availability but not purchase cost | No repair screen unless separately granted | Current rules already check `reparation` for repair docs and freeze certain technician fields; preserve this. Add owner scoping on all linked product reads/writes. |
| Repair delivery/payment | `reparation` plus owner authority | No delivery/cash | `pos` may deliver/collect under existing cash design | Rules must preserve the current no-technician-cash condition, not just hide controls. |

Add candidate keys `pieces`, `comptabilite`, and `personnel` only as menu entitlements on existing `role: 'admin' | 'user'` profiles. Define explicit defaults for new users without changing existing profile role values.

## 6. Money rules and accounting model

### Precision

The application already uses `Math.round(x * 1000) / 1000` in user-facing money flows, including POS, invoices, and client settlement ([src/components/POS.tsx:448-448](../src/components/POS.tsx:448), [src/components/Invoices.tsx:162](../src/components/Invoices.tsx:162), [src/components/Clients.tsx:173-183](../src/components/Clients.tsx:173)). For new modules, use **integer millimes** as the authoritative stored/computed unit (`1 DT = 1000 millimes`): parse/validate input once, convert to a safe integer, do additions/subtractions/multiplication by integer quantity, and convert to display dinars only at UI boundaries. For percentage/tax calculations, round once to the nearest millime using the documented `Math.round` policy. Existing numeric dinar fields should remain unchanged until individually migrated and reconciled; do not silently reinterpret them as millimes.

### Single accounting journal; no double counting

Create an owner-only append-only `accounting_entries`/journal with stable `entryId`, `ownerId`, `eventType`, `sourceType`, `sourceId`, optional `employeeId`/`periodId`, `amountMilli`, debit/credit account codes, `occurredAt`, `createdBy`, and a reversal/reference field. Use deterministic event IDs (for example source document + event type + installment ID) so retries cannot create duplicate journal effects. Corrections use linked reversal entries.

- **Sales, repairs, and receipts:** recognize sale revenue once on the sale event; invoice is a linked document, not a second revenue event. Recognize repair revenue once at the chosen completion/delivery event (recommended: delivery), with discounts/refunds represented as linked adjustments. When money is collected later, debit cash and credit customer receivable; do not record revenue again. Allocate partial receipts to specific open sale/repair balances. Client balance should be a derived/reconciled total from receivable entries rather than an independently edited figure.
- **Inventory purchases:** a stock receipt/purchase is inventory asset on receipt/payment, not an operating expense merely because it was purchased. Recognize cost of goods sold once when units are sold or consumed in a repair: debit COGS, credit inventory. This prevents counting the same `supplies` purchase as an expense and then counting the same part cost again in sale/repair margin. The current dashboard's supplies totals and sale COGS are separate measures and must not simply be combined as a single net-profit calculation ([src/components/Dashboard.tsx:477-511](../src/components/Dashboard.tsx:477), [src/components/Dashboard.tsx:429-471](../src/components/Dashboard.tsx:429)).
- **Other expenses:** record rent, utilities, fees, etc. once when the chosen accounting policy recognizes them (default: expense when incurred/approved, with a payable until paid); a payment settles that payable rather than creating a second expense.
- **Salary and bonus:** on approval/close of a payroll period, recognize gross salary and approved bonus as wage expense and create wages payable once, with a unique employee/period run ID. A salary payment—full or partial—reduces wages payable and cash; it is not a new expense. Outstanding wages equal payroll liability less linked payment allocations.
- **Advances against earned salary:** an advance payment before payroll close is a recoverable employee advance/receivable, not a second wage expense. At payroll close, apply the authorized amount once against wages payable/advance receivable, then pay the remaining net amount. If advance is paid after payroll is accrued, it is simply a partial settlement of payable.
- **Separate employee loans:** loan disbursement creates an employee-loan receivable and reduces cash, not a wage expense. Repayment reduces that receivable and increases cash; it is not revenue and must not also be counted as a salary deduction. If deductions are taken from a paycheck, allocate them to loan repayment and reduce the loan balance once.
- **Bonuses / outstanding amounts:** recognize an approved bonus with the payroll accrual; bonus payment reduces the same payable. Payroll status must distinguish draft, approved/accrued, partially paid, and paid. Unpaid wage/bonus balances remain liabilities; loan balances remain receivables. A single journal links all advances, repayments, and partial salary payments to the payroll/loan source IDs.

Do not repurpose `supplies` or `client_debts` as a complete ledger. Both are existing operational records with limited scope.

### Architecture blocker / server-side requirement

The existing Express/Firebase Admin server proves server-side code is possible, but its checked endpoints are user administration, PDF, and OTP—not stock, cost, accounting, or payroll ([server.ts:86-93](../server.ts:86), [server.ts:246-247](../server.ts:246), [server.ts:325-393](../server.ts:325)). There is no evidence here that it is deployed, backed by a configured production service account, or included in the current hosting route. Before selecting a server-only transaction design, confirm hosting, authentication, environment/secrets, and operational ownership. If the business requires guarantees that untrusted browsers cannot bypass for stock/ledger mutations, implementing and deploying a trusted transaction endpoint (or equivalent Cloud Function) is a prerequisite; rules and UI alone are not a substitute. No deployment was attempted.

## 8. Decisions needed (recommended defaults)

1. **Canonical spare-part stock:** keep one stock in `products` or approve a coordinated `parts` migration? **Default: keep `products` canonical and add an explicit spare-part marker.**
2. **Who can see costs and margins, including platform super-admin accounts?** **Default: only the store's own `admin` (`uid == ownerId`); no technician/cashier or cross-store override.**
3. **When are repair parts deducted and returned?** **Default: reserve/deduct when a ticket is created or parts are added; status-only changes do nothing; cancel/delete releases once; delivery consumes the reservation; reopening does not deduct again.**
4. **Should technicians have a separate parts-list menu?** **Default: no; show name/reference/availability/selling price in the existing repair workflow only.**
5. **Reference/barcode uniqueness scope and normalization?** **Default: unique within each store, with separate namespaces for reference and barcode; trim/case-fold references and normalize barcode input consistently.**
6. **Inventory purchase accounting policy?** **Default: capitalize stock receipts as inventory and expense COGS only on sale/repair consumption; recognize non-stock operating expenses when incurred/approved.**
7. **Payroll recognition and advance/loan treatment?** **Default: accrue salary/approved bonus once when payroll is approved; payments settle payable; salary advances are receivables until applied; separate loans are receivables and repayments are not income.**
8. **May the existing Express server be deployed/extended for trusted stock and ledger commands, or is a Cloud Function required?** **Default: use a trusted server-side transactional command path, subject to confirming current hosting and security operations before implementation.**
9. **How should existing records with missing historical cost be reported?** **Default: mark as unknown/estimated and exclude from audited margin totals until reconciled; never silently substitute today's cost.**
